# Internationalisation

The site is bilingual from the first converted page. There is no phase in this project where
hardcoded user-facing strings are acceptable.

The library is **chosen in BRA-3** (with the first converted page). The rules below hold whatever
it is, and they apply now: no user-facing string literal goes into `src/` outside a locale file.

## Supported locales

| Code | Language | Status  |
| ---- | -------- | ------- |
| `ru` | Russian  | default |
| `en` | English  | full    |

The locale codes come from `src/shared/config`. Today that file holds only `DEFAULT_LOCALE`
(used for `<html lang>`); the full locale list arrives with the library in BRA-3.

The visitor's choice is stored under `conn_lang` as a plain string (`ru` or `en`), shared with the
legacy pages, so switching language on one page carries over to the others. See
`state-management.md`.

## Rules

- **`ru` and `en` together.** When you add a key, add it to both locales in the same change. A key
  that exists in only one locale is a bug.
- **Name a key after what it means, not what it says.** `actions.submit`, never
  `sendYourReviewNow`. The text can change without touching any component.
- Keys are `camelCase`, nested at most two levels, grouped by the UI region they appear in.
- **Never concatenate translated fragments.** A sentence is one key with interpolation, because
  word order differs between languages.
- Never nest a translated result inside another translation call.
- Keys are typed: a wrong key is a type error. Whatever library BRA-3 picks must support that.

## Plurals

Use the library's plural forms, never a manual ternary. English needs `one` and `other`; Russian
needs `one`, `few`, `many` and `other`. This is exactly why plural logic does not belong in
components.

```json
{
  "reviewCount_one": "{{count}} отзыв",
  "reviewCount_few": "{{count}} отзыва",
  "reviewCount_many": "{{count}} отзывов",
  "reviewCount_other": "{{count}} отзыва"
}
```

Plural categories come from `Intl.PluralRules` for the active locale.

## Formatting

Dates, numbers and relative times go through helpers in `shared/lib/format`, which wrap
`Intl.DateTimeFormat`, `Intl.NumberFormat` and `Intl.RelativeTimeFormat` with the active locale.
Never format a date or a number by string concatenation, and never hardcode a separator. The visit
counter is a formatted number too.

## Static rendering

Pages are generated at build time, so the HTML is rendered in the default locale and the client
switches after hydration (see `state-management.md` → "Hydration and the theme flash"). If BRA-3
moves to per-locale static routes instead, record that decision here.

## Interface language vs review language

- **Interface language** is what this document covers.
- **Review language** is the language a visitor wrote in. A review is stored in its original
  language and translated once, on approval, into the other locale. The translation is untrusted
  model output and is rendered as plain text, exactly like the original.
